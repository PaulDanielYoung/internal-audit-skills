# Request messages and reminders

Render the selected rows from the list as the source of truth:

- Initial or additional request: selected **Proposed** rows only.
- Reminder: selected outstanding **Requested** rows only.

Apply an addressee filter when requested. If selection is materially ambiguous, settle it with the auditor before drafting. Preserve each selected deliverable's wording, period/version, and auditor-supplied due date. Identify the RQ IDs so replies can be matched. Keep unrelated rows out of the message.

Produce the communication alone in a clearly separated part of the reply; put assumptions, supporting sources, methodology basis, and unresolved internal gaps outside it. Messages are one-off replies, never persistent artifacts. Drafting changes no list state. This skill sends no email.

When the auditor confirms that an initial/additional message was actually sent, apply the Requested transition in LIST-RULES.md to the confirmed rows using the actual date. If that date is missing, ask for it rather than assuming today's date. A confirmed reminder preserves each row's original Requested date and appends the actual follow-up date and relevant details to Notes.
